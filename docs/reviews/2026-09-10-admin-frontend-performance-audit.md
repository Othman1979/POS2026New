# Admin frontend performance audit — 2026-09-10

This is the preserved baseline audit. The subsequently authorized fixes and their measured results are recorded in [the implementation follow-up](2026-09-10-admin-frontend-resource-cuts.md).

**Audit only.** Five targeted opportunities are supported by browser or source evidence. The strongest responsiveness issue is synchronous spreadsheet inspection; the clearest loading saving is deferring SheetJS. Large sales reports also create measurable rendering stalls. No application source, backend, database, UI design, deployment kit, or configuration was changed. Nothing was pushed, merged, or deployed.

## Evidence and reproduction

Audited frontend: `61ab4e386fd22f1029f69a0ff57b0a05236a4645`, branch `codex/admin-frontend-audit`. A path-scoped Git comparison confirmed the admin/shared frontend, business utilities, Vite config and admin HTML are unchanged by backend commit `65487f71`.

- Harness: [admin-frontend-audit.cjs](admin-frontend-audit.cjs).
- Recorded samples, request paths, resource bytes and heap counters: [2026-09-10-admin-frontend-measurements.json](2026-09-10-admin-frontend-measurements.json).
- Local raw results/screenshots: `scratch/admin-frontend-audit/` (ignored; regenerated by the harness).

From the repository root with its Node dependencies and Playwright Chromium installed:

```powershell
npm run build:admin
$env:AUDIT_ROUNDS='3'
$env:AUDIT_CPU='1'
node docs/reviews/admin-frontend-audit.cjs
$env:AUDIT_CPU='4'
node docs/reviews/admin-frontend-audit.cjs
```

Run sequentially with other benchmarks stopped. Windows, Intel i7-14700KF, Node 24.16.0, Chromium 148.0.7778.96; production Vite build succeeded. The existing JavaScript Playwright dependency was used because this machine's Python environment lacks Playwright.

Each rate uses three fresh contexts for English desktop (1440×900) and Arabic mobile viewport (390×844). These paired configurations **do not isolate language from viewport effects**. A standalone loopback server serves built assets with gzip and synthetic GET responses plus a local Socket.IO transport. It imports no application server/database code, rejects non-GET requests, blocks browser requests outside its origin, and supplies an authenticated fixture session. Spreadsheet selection stops before submission.

Fixtures: 2,000 catalog products / 40 categories; ordinary inventory pages of 12 and 96; 50 orders and 50 customers; sales reports with 100 products and a **2,000-product stress case**; a 2,438,402-byte legacy workbook with 20,000×16 cells. Customer data distributions, network latency, authentication, actual backend response costs, editor interactions and physical-device RAM are not measured.

## Ranked findings and proposed fixes

1. **High — selecting a workbook blocks the UI before upload.** `src/admin/components/ImportModal.vue:266–299` performs `XLSX.read`, full `sheet_to_json`, a width scan, and full-column `map/filter` operations synchronously after `arrayBuffer()`. The measured workbook produces a multi-second throttled long task; backend import workers cannot remove this browser stall. **Propose:** run inspection in a short-lived browser worker, transfer the ArrayBuffer, and return only sheet/mapping metadata and bounded samples. Stop scanning a column after sufficient samples; retain supported workbook/legacy mapping behavior, error feedback and latest-file cancellation. Keep authoritative import validation unchanged. Verify file selection, removal/replacement and template generation in both languages; show responsive progress throughout. Worker memory and timing savings are not yet measured.

2. **High confidence, small change — avoid eager SheetJS on Inventory entry.** `src/admin/pages/Inventory.vue:733` statically imports `ImportModal`; its `v-if` at line 716 prevents mounting, **not downloading/evaluating**, the dependency imported at `src/admin/components/ImportModal.vue:218`. Browser traces show 160,635 gzip bytes for SheetJS out of 206,392 new JS body bytes on Inventory entry. **Propose:** load the inspection worker/SheetJS on import or template intent; keep opening the dialog immediate with explicit loading state. This defers 160.6 kB until needed, not a permanent saving once used. Do not split the Inventory file merely because it is large.

3. **Medium, scale-dependent — sales report mounts every matching product.** `src/admin/pages/ReportsSalesDetails.vue:132` renders the complete `filteredProducts` list, recomputed from input at lines 228–236 without a mounted-row bound. **Propose:** reuse the application's simple pagination pattern for this table, preserving full-period totals, search/category semantics and complete print data. Consider windowing only if continuous scrolling is a requirement. Verify the 100/2,000-product fixtures, keyboard access, RTL and printed totals before accepting a change. An implementation benefit has not been measured; the present rendering cost has.

4. **Medium — Inventory repeats unrelated reads and fans out event bursts.** `src/admin/pages/Inventory.vue:863–912` fetches products **and all categories** for each search/page change; `handleInventoryChange` at line 975 bypasses the existing same-tick `reload` coalescer. A single search produces two GETs. Ten same-tick inventory events produce **20 GETs: 10 products + 10 categories**. Sequence checks discard stale results but do not cancel that work. **Propose:** reuse loaded categories during ordinary product filtering/paging; refresh them on activation, relevant inventory/settings signals and category writes. Coalesce event reads with one in-flight request plus one trailing dirty refresh, retaining generation checks and immediate explicit user refreshes. Validate a change arriving during the in-flight read so the final catalog stays fresh. Event frequency and production byte savings are unmeasured.

5. **Lower priority — sidebar badge independently reloads per JoFotara event.** `src/admin/components/Sidebar.vue:157–183` reads `api/admin/jofotara/operations?limit=100` on each event. Ten injected notifications cause **10 GETs**, even outside the operations page. **Propose:** a small in-flight/dirty coalescer in this existing component, preserving initial load and final-state refresh. Do not add a new global state layer or change backend APIs for this finding. The fixture returns an empty disabled result; real payload costs and event burst frequency are unknown.

## Memory, reactive work and boundaries

- In the 4× CPU runs, forced-GC JS heap after cold dashboard is approximately **4.2–4.3 MiB**. After visiting the measured pages and returning to dashboard it is **10.6–10.8 MiB**, then approximately **11.1–11.3 MiB** after five Orders → Inventory → Sales → Dashboard cycles. Warm DOM counters stabilize near **13,392 nodes / 1,322 listeners**, while only 287 elements are connected to the dashboard document. `src/admin/App.vue:90` deliberately caches dashboard/orders/inventory; detached cached DOM and loaded module code explain some retained state. The remaining roughly 0.5 MiB growth is **not attributed**: code warming, resource instrumentation and app caches are possible contributors. This short run neither proves a leak nor establishes long-session stability; no cache removal is justified from it.
- Orders and Inventory each create desktop and mobile representations (`src/admin/pages/Orders.vue:206,285`; `src/admin/pages/Inventory.vue:220,275`). Their datasets are bounded; 96 inventory items create 5,889 connected elements. Conditional rendering by breakpoint is a possible later experiment, but its incremental benefit is unmeasured and resize/focus behavior must survive. Do not add virtualization to every table.
- The dashboard controller uses a shallow payload, coalesced refreshes and deactivation/visibility cleanup (`src/admin/composables/useDashboardData.ts`). System settings are shared through `src/shared/systemSettings.js`; the cold flow makes one settings GET, not one per consumer. Ten-second idle samples make no API reads and no long tasks. Report formatters already cache Intl instances (`src/admin/utils/reportFormatting.js`). Preserve these mechanisms.
- `src/shared/i18n/runtime.js:156–170,280–344` combines component lifecycle translation with a MutationObserver/tree walk. Its share of route cost is **unprofiled**; do not disable it to improve numbers. Likewise, the header's minute-only clock ticks every second (`src/admin/components/AdminHeader.vue:253–270`), but measured overall idle work is low. Neither warrants priority over the measured stalls.
- Routes are already lazy (`src/admin/pageRegistry.js`); PDF generation is already dynamically imported (`src/admin/pages/Orders.vue:910`). No duplicate bundled Socket.IO client, PDF payload, POS entry or print-template editor was downloaded during the measured dashboard/list flows. Keep those boundaries. Font/icon subsetting and removing the apparently unused global Vue export (`src/admin/bootstrap.js:28`) are **build/profile hypotheses**, not verified savings.

All final fixture runs completed without browser errors or unmapped endpoints. Direction flags and sampled screenshots were inspected; this is not exhaustive translation, print or transaction acceptance. No proposed optimization was implemented, so the report claims measured baseline costs and byte opportunities, not achieved savings.
