# Focused verification

## Core commands

Read this first. Everything else is per-area; search for the area you touched.

Run commands from the repository root. Preserve `.env` and `.env.test`; neither belongs in commits.

- `npm run test:frontend -- <file-or-filter>` runs the `src/**/*.spec.js` tests without MySQL or the Express server. It supports Vue components through the existing Vite plugin.
- `npm run test:isolated -- <file-or-filter>` runs the existing Vitest suite against a newly generated loopback database. It reuses the guarded review preload, passes normal Vitest options through, and removes only the database it successfully created. Test failures retain a failing exit code. Raw JSON evidence can be saved under ignored `scratch/` with `--reporter=json --outputFile=scratch/result.json`.
- `npm run test:isolated:shards [-- --shards=N] [-- <filter> ...]` runs the whole suite (or the matching files) in about five minutes instead of about 85. Each shard is a separate `test:isolated` run against its own throwaway MariaDB server, started from the local MariaDB binaries (`POSAPP_TEST_MYSQL_BIN`, default `C:/xampp/mysql/bin`) on its own port (`POSAPP_TEST_SHARD_PORT`, default 3401) and datadir, with no fsync and one shared tablespace; servers are shut down and their datadirs deleted afterwards, and the developer database is never touched. A single shared server does not scale: `seedDatabase` drops and recreates every table before each test, and one server serializes that schema work across shards. Files are balanced by their last measured duration (ignored `scratch/test-shards/durations.json`); a file longer than an average shard (`tables.test.js`, `checkout.test.js`) is split into test-name parts using the previous run's per-test durations, and the last part runs every name the earlier parts do not list, so new tests are never dropped. Shards run with `--no-cache`. Build first (`npm run build`) because some integration tests serve `dist/`. Per-shard logs and JSON reports go to `scratch/test-shards/`. Confirm a failure that only appears in parallel by rerunning that file alone with `npm run test:isolated -- <file>`.
- `npm run build:admin` verifies the production frontend build.
- Spooler checks are separate: `node pos-spooler-printer/tests/<name>.test.js`. Use the packaged Node runtime when checking the installed spooler environment.

The isolated runner loads local test connection credentials from `.env.test` when present, or uses loopback/root defaults. Both the fixture seeder and Vitest lock validate the destination before connecting and honor `DB_PORT`. They reject application database names and remote hosts. The accepted fixture names are `posapp_test` and generated `posapp_review_recipe_p1_<12 hex>` names; the latter spelling is retained for compatibility with existing review scripts.

For pool-capacity checks, set `POSAPP_REVIEW_CONNECTION_LIMIT` to a valid capacity before using the runner. The preload reapplies this test-only override after every environment load; a plain `DB_CONNECTION_LIMIT` can be overwritten by `.env.test`. The connection-lifetime regression asserts the effective driver capacity when this override is supplied.

Do not run two full backend suites concurrently. Several migration integration files create their own fixed, explicitly named test databases outside the runner's generated database. The existing Vitest lock serializes runs sharing the same primary database; it cannot serialize those separate migration fixtures across different generated databases. A killed process may leave its generated database for later explicit cleanup.

`npm run test:unit` runs backend integration and frontend tests, and its pretest hook compares the configured development and test schemas. Prefer the focused commands above when that comparison is unrelated to the change. This does not replace required Release gate checks.

For a full review, use `--reporter=default --reporter=json --outputFile.json=scratch/result.json` and retain the console log too. Vitest's JSON report can list a failed suite with skipped cases and an empty message when a setup hook fails; the default reporter preserves the underlying hook error.

The Release gate requires all application shards, Windows installer tests, spooler tests, and the browser-workflows job on every PR and master push. After building, run `npm run test:release-browser` for the same sequential staff/table/payment, stale-void, and checkout-recovery browser checks locally. Install Chromium with `npx playwright install chromium` first (CI uses `--with-deps`). The command rejects missing/incomplete English/Arabic evidence and failed fixture cleanup; baseline-only review modes cannot satisfy it. Browser reports/screenshots are uploaded from CI, and failed database jobs capture bounded container state (including OOM/exit status), logs, resources and InnoDB diagnostics. A skipped, missing or cancelled required job fails the aggregate gate.

For backend startup/resource comparisons, run `node scripts/reviews/schema-query-experiment.cjs <baseline-commit> <fresh-sql-path>` and `node scripts/reviews/backend-resource-experiment.cjs <baseline-commit>` separately from other workloads. The schema experiment creates/removes its own guarded loopback database, imports the supplied baseline, compares ledger/schema checks, and verifies both validators reject a deliberately removed authority index. The resource experiment uses fresh subprocesses, synthetic workbook/log data, and no database. Results go to ignored `scratch/backend-startup-comparison.json` and `scratch/backend-resource-comparison.json`. Module RSS savings are not additive estimates of Hostinger process memory; worker parsing can increase total import CPU/time while reducing main-thread stalls.
